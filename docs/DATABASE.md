# Local Database Design — ARTHIKA

## 1. Persistence principles

- Expo SQLite is the approved local relational database.
- Financial data is the source of truth; UI state is not.
- Use database transactions for multi-record financial operations.
- Use migrations with explicit schema versions.
- Persist money in integer minor units where practical.
- Index common source/date/status queries.
- Never store a PIN in plain text.
- Keep SQL behind a small data-access/repository layer; screens should not contain raw SQL.

Direct Expo SQLite was approved for the MVP following the
[data-access comparison](./DATA-ACCESS-RECOMMENDATION.md). Connection ownership,
serialized access, and migration infrastructure are implemented. Phase 3.2 adds
the money-source table and typed repository; Phase 3.3 adds the transaction
ledger table and repository. Phase 3.6 verifies that sources, transactions, and
the balances derived from them survive a full close/reopen cycle (an app
restart). The current schema version is three: `money_sources`, `transactions`,
and the `is_voided` transaction flag backing the void-and-reverse correction
policy. Other product tables and screen integration remain separate roadmap
subtasks.

## 2. Proposed entities

`money_sources` and `transactions` are implemented. Other entities below remain
conceptual; refine them in their own subtasks, not all at once.

### `money_sources`
`id`, `name`, `type` (bank/cash/wallet), `opening_balance_minor`, `currency_code`, `is_archived`, `created_at`, `updated_at`.

Implemented in migration 1. IDs are stable opaque 128-bit random hex strings
generated by SQLite (not UUID-formatted). Names are trimmed/non-empty; display
names need not be unique. Source types and the archive flag have SQL constraints.
Opening balances are signed safe-integer minor units, including zero; unlike an
expense magnitude, a starting balance can represent a negative position. Both
SQL and the repository reject fractional/out-of-safe-range values.

Currency is explicit: the repository accepts three uppercase ASCII letters,
without choosing a default, validating a currency registry, or converting money.
Supported UI currencies/precision and setup defaults still need a product decision.
Timestamps are UTC ISO strings. The repository supports creation, lookup, active
or inclusive listing, non-financial name/type edits, and idempotent archiving.
It exposes neither deletion nor changes to opening balance/currency. Archive
preserves IDs and rows for historical references. A later reconciliation flow
will record balance corrections rather than rewrite opening balances.

### `transactions`
`id`, `type` (expense/transfer/adjustment), `direction` (debit/credit),
`amount_minor`, `source_id`, nullable `description`, nullable `payment_method`,
`occurred_at`, timestamps. Implemented in migration 2 with positive safe-integer
amounts, a foreign key to `money_sources`, and indexes for source/date and
type/date reads. The repository currently creates expenses and debit/credit
adjustments, provides lookup/listing, and exposes a minimal
source/direction/amount projection for balance calculation. It does not create
transfers, categories, voids, or edits yet. Future schema additions (category,
transfer linkage, EMI occurrence linkage, void status) belong to their own
roadmap subtasks and migrations.

### `transfers`
`id`, `from_source_id`, `to_source_id`, `amount_minor`, `occurred_at`, nullable `note`, timestamps. May be paired with ledger entries depending on chosen implementation.

### `categories`
`id`, `name`, `icon_key`, `sort_order`, `is_archived`; optional type for future income support.

### `emis`
`id`, `name`, `monthly_amount_minor`, `currency_code`, due schedule, `start_date`, nullable `end_date`, nullable `total_installments`, nullable `preferred_source_id`, nullable `payment_method`, nullable lender/notes, lifecycle status, reminder configuration, timestamps.

### `emi_occurrences`
`id`, `emi_id`, `due_date`, `amount_minor`, status, nullable `paid_at`, nullable `linked_transaction_id` (unique where present), timestamps. Enforce unique EMI/schedule occurrence identity.

### `reconciliations`
`id`, `source_id`, `previous_balance_minor`, `actual_balance_minor`, `difference_minor`, nullable reason, `created_at`, linked adjustment reference.

### `app_settings`
Typed settings or key/value settings for privacy, theme, notifications, lock enabled state/timeout, currency/locale. Raw PIN must not be stored here; secure credential material belongs in platform secure storage.

## 3. Constraints

- Expense references one source.
- Transfer references two different sources.
- EMI occurrence references one EMI.
- A paid occurrence links to at most one expense.
- An expense links to at most one EMI occurrence.
- Reconciliation references one source and one adjustment.
- Historical references remain valid after source archive.
- Transfer and EMI payment writes are atomic.
- Amounts are positive magnitudes; direction comes from type/relationship.
- Enable foreign-key enforcement.

## 4. Balance query strategy

Prefer deriving balances from opening balance plus ledger events, or use a controlled cached balance updated in the same transaction as each ledger event. Never let screens independently mutate cached balances. Provide recomputation/verification if caching is used.

Implemented in [balance.ts](../src/domain/balance.ts) as pure functions. A
credit adds and a debit subtracts, so expenses, adjustments, and future paired
transfer entries use the same rule. The module returns per-source balances and
totals grouped by currency; it does not convert currencies, filter archived
sources, or write a cached balance. Callers pass exactly the sources and entries
they want included. A transfer must be supplied as a paired debit and credit;
the balance function can verify the arithmetic but cannot enforce an atomic
transfer write.

## 5. Backup format

- Include schema version.
- Include all records needed to restore, preserving IDs and relationships.
- Validate before import.
- Use atomic/staged import.
- Exclude secrets such as PIN verification material.
- Define replace vs merge policy; do not guess.
- Version format for future migrations.

## 6. Sequence

1. Validate Expo SQLite and migration approach.
2. Create schema/migration foundation.
3. Implement source persistence.
4. Implement transaction persistence and balance queries.
5. Add atomic transfers.
6. Add reconciliation records.
7. Add EMI and occurrence persistence.
8. Add backup/restore after the data model stabilises.
